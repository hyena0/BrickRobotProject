# Stage 5D: Generated Robot: Design, Round Trip and Physical Build

**Status: draft add-on, not merged.** Defined by `PLAN.addendum-generated-robot.md`. Existing stage docs and `PLAN.v2.md` are unchanged; this document is merged into them only when the schedule confirms it.

**Goal:** from a desired kinematic specification, generate an original LEGO arm by combining in-house joint modules, verify it virtually by feeding it back into the inference pipeline (round trip), **rebuild it physically**, and make it the **public hero robot** whose control logic is generated by the same pipeline and then extended to the VLA (Stage 6B v2).

**Why:** the MR JOS-based robot cannot be published. A robot designed by our own generator from our own modules is fully publishable: model, meshes, renders, physical footage and VLA data.

**Relation to existing docs:** extends the Stage 7 procedural generator idea from random to specification-driven generation. Stage 7 doc is kept unchanged; its generator may reuse this code.

## Two phases

| Phase | Tasks | Depends on | When |
|---|---|---|---|
| **Phase 1: independent** | 5D.0–5D.7 (inventory, modules, spec, design agent, generator, round trip, renders, build outputs) | Committed code of Stages 1–5 and 5A (5A outputs are read-only, not required by Phase 1) | **After the 5A commit, in parallel with 5B** |
| **Phase 2: after 5A** | 5D.8 physical build, 5D.9 limits + robot package + control logic for the generated robot | 5A tools and package format merged; MR JOS footage done (Day 6) | Day 6–7 |

**Order:** finish 5A → commit Stage 5 + 5A together on main → create the 5B and 5D worktrees from that commit. Human-only prep (spare counting, Studio modules, Modal setup) can start before the commit.

Phase 1 does not need `docs/robot_package.md` or any 5A output. Expected kinematics use the existing kinematic schema (`docs/schema.md`).

## Running in parallel with 5A

### Workspace

```bash
git worktree add ../MetaHack-5d -b stage-5d
cd ../MetaHack-5d
```

All 5D work happens in this worktree on branch `stage-5d`. Merge into main only after 5A is merged (rebase first).

### File ownership

| 5D may modify | 5D reads only | 5D never touches |
|---|---|---|
| `src/gen/`, `assets/modules/`, `specs/`, `generated_robots/`, `scripts/heavy_guard.sh`, `src/render/modal_render.py`, `src/catalog/parts_5d.yaml` (overlay), tests under `tests/gen/` | `src/parse/`, `src/catalog/parts.yaml`, `src/tools/`, `src/agent/`, `src/kin/`, `src/verify/`, `src/codegen/`, `src/viz/pose_*.py`, `docs/schema.md` | `src/limits/`, `src/package/`, `src/viz/export_visual_pack.py`, `docs/robot_package.md`, `config/homing*`, `generated/robot_inferred/`, `runs/stage5a/`, any running 5A process |

- **Catalog overlay:** new parts used by modules go into `src/catalog/parts_5d.yaml`; the loader merges it after `parts.yaml`. This avoids conflicts with the main catalog.
- **Blender MCP:** only the 5D session connects to Blender MCP.

### Local resource avoidance (5A is running)

1. **Batch renders run on Modal by default** (5D.6). Local machine only downloads results.
2. **Local Blender** (LDraw → `.glb` conversion, Blender MCP checks) only after `scripts/heavy_guard.sh` passes:
   - no other Blender process (`pgrep -fl -i blender`),
   - Blender MCP port not in use by another process (`lsof -i :<port>`),
   - 1-minute load average ≤ 70 % of CPU cores (`uptime`, `sysctl -n hw.ncpu`).
   If any check fails: wait 5 min and retry, up to 30 min; then skip the job and log it in `LOG.md`.
3. **Low priority locally:** `nice -n 15`, `OMP_NUM_THREADS=2`, Blender `--threads 2`.
4. **Own serialisation:** every heavy local 5D job takes `/tmp/metahack-heavy.lock` with `flock`. (When 5A is restarted later, it can use the same lock.)
5. **Never** kill, pause or modify 5A processes or files.

`scripts/heavy_guard.sh` exit codes: `0` free, `10` busy (retry later), `20` timed out (skip).

### Shared API limits

Spark Contributor limits (150 RPM, 3M TPM) are **shared with the 5A session**.

- Design agent and round-trip agent: one run at a time.
- Muse Code subagents in this session: at most 2 in parallel.
- Exponential backoff on 429 (already required by `AGENTS.md`).

## Scope (reduced on purpose)

- Serial arm, **3–4 joints** (+ optional gripper), straight chain.
- **3–4 hand-made modules**, no automatic pattern extraction from other designs.
- **Buildable from parts on hand**; preferably **one EV3 brick** (≤ 4 motors, ≤ 4 sensors).
- Virtual verification first, then physical build.

## Constraints for physical rebuild

| Constraint | Rule |
|---|---|
| Inventory | `config/inventory.local.yaml` (private) = MR JOS robot's parsed part list (exact counts from Stage 1) + manually counted spares. The generator's bill of materials must fit it |
| Optimisation | 1) fits inventory, 2) meets spec within tolerance, 3) fewest distinct part types, 4) fewest parts, 5) prefer high-stock parts |
| Motors | Large motors on load-bearing joints (shoulder, elbow); medium motors on base yaw and wrist |
| Brick and ports | One brick if possible: ≤ 4 motors and ≤ 4 sensors. Port wiring is part of the design output |
| Homing | Each module carries a touch-sensor mount where possible; joints without a sensor use stall homing |
| Cable reach | Motor and sensor positions within cable reach of the brick (approximate distance check) |
| Disassembly order | Parts come from the MR JOS-based robot: finish and film all its physical work (5C) first |

## Phase 1 tasks (independent)

### 5D.0 Inventory · `config/inventory.local.yaml`

- Export the MR JOS robot's part counts from `parts.json` (Stage 1, private) with a script; add spares counted by hand (motors, sensors, turntables, gears, beams by length, axles by length, pins).
- Mark scarce parts (motors, sensors, brick, turntables, large gears) as hard limits.
- Private: it describes the MR JOS design's parts.

### 5D.1 Module library (human in Studio) · `assets/modules/`

Modules are designed **only from inventory parts**; each manifest lists its own BOM.

| Module | Example content | Joint |
|---|---|---|
| `M_base_yaw` | Turntable + pinion + motor mount | Revolute, vertical axis |
| `M_pitch_worm` | Worm + gear + motor (self-locking) | Revolute, horizontal axis |
| `M_pitch_direct` | Low-ratio spur stage + motor | Revolute, horizontal axis |
| `M_wrist_roll` (optional) | Small gear stage + motor | Revolute, along the arm |

Manifest per module (`module.json`): input mount frame, output mount frame, joint axis in module frame, gear ratio, motor type, **designed range**, sensor mount, size, BOM. Modules are original work, published under the repo licence.

Connectors: straight Technic beams of length 3–15 holes between modules (8 mm per hole).

### 5D.2 Specification · `specs/<name>.json`

```json
{"joints": ["yaw", "pitch", "pitch", "roll"],
 "link_lengths_mm": [0, 120, 100, 40],
 "ranges_deg": [[-150, 150], [-30, 100], [-120, 120], [-180, 180]],
 "gripper": false}
```

### 5D.3 Design agent (Spark) · `src/gen/design_agent.py`

- Input: specification + module manifests + inventory summary (counts only).
- Spark chooses a module per joint and beam lengths (rounded to 8 mm) to match link lengths and ranges; explains choices.
- Generator assembles; checks reach, rounding error, zero-pose collisions and BOM vs. inventory; reports back with the optimisation score (part types, part count, scarce parts used). Spark revises (max 3 rounds).
- Output: `generated_robots/<name>/robot.ldr` + `expected_kinematics.json` (known by construction; `docs/schema.md` format) + designed ranges.

### 5D.4 Generator · `src/gen/assemble.py`

- Deterministic placement: compose module frames along the chain, insert beams, snap to the stud grid, write LDraw.
- Pre-check: no overlapping parts at the zero pose (BVH, run under `heavy_guard` + lock, low priority).

### 5D.5 Round-trip verification · `src/gen/roundtrip.py`

- Run the Stage 1–5 pipeline (simulation part) on `robot.ldr` **with no hints** (the agent does not see `expected_kinematics.json`).
- Compare: joint count, axis angle error, axis distance, gear ratios, link lengths, IK end-effector error (Gate 1 and Gate 2 thresholds).
- Results to `generated_robots/<name>/roundtrip.json` and a short line in `LOG.md`.

### 5D.6 Visuals (Modal render) · `src/render/modal_render.py`

| Step | Where |
|---|---|
| LDraw → `.glb` per link (generated robot only) | Local, guarded |
| Blender MCP visual check (links coloured, axes) | Local, guarded, 5D session only |
| Batch renders: multi-view, safe poses, video frames | **Modal** |

- Modal image with the **same Blender version as local** (pinned); Cycles on GPU (L4 or A10G class).
- Inputs: `.glb` files + `render_job.json` (cameras, resolution, samples, poses) uploaded to a Modal Volume.
- One function call per view/pose, run with `map`; timeout 20 min per call; outputs downloaded to `generated_robots/<name>/renders/`.
- Only generated-robot assets go to Modal. MR JOS files never leave the Mac.
- Estimated cost: $2–5 of the Modal $100.

### 5D.7 Build outputs · `generated_robots/<name>/`

- `bom.json`: bill of materials, checked against the inventory.
- `robot_steps.ldr`: model with LDraw `STEP` lines in build order (module by module).
- `wiring.yaml`: planned motor/sensor → brick/port assignment (same format as `config/ports.local.yaml`).

## Phase 2 tasks (after 5A is merged)

### 5D.8 Physical build and check (Day 6 afternoon)

**Disassembly checklist (before touching the MR JOS robot):** all 5C physical runs filmed; 5C report, port map and measurements saved; photos from all sides; the private `.io` kept for a later rebuild.

1. Build from `robot_steps.ldr` and `bom.json`; wire according to `wiring.yaml`.
2. Photograph the built robot from the render's front/side/top viewpoints.
3. Compare link lengths with a ruler vs. the model (±3 mm); joint directions by hand vs. the model.
4. Record differences in `LOG.md`; if a module changed during the build, update the model and re-run the round trip.

### 5D.9 Limits, robot package and control logic for the generated robot

- Initial limits from the modules' designed ranges; 5A tools check fold collisions between modules (coupled constraints) and build the robot package.
- New robot package + `wiring.yaml` → controller package (5C). Run the 5C wizards: homing, directions, limit capture, safe pose replay, Cartesian test.
- This control logic is the base for the VLA (Stage 6B v2).

## Exit criteria

**Phase 1**

- [ ] Inventory file built; scarce parts marked.
- [ ] 3+ modules with manifests; validator checks frames, axis and BOM against the inventory.
- [ ] Design agent produces a robot for the reference specification within 3 rounds; BOM fits the inventory.
- [ ] Round trip passes Gate 1 and Gate 2 thresholds on the generated robot.
- [ ] Renders produced on Modal; step file and wiring plan generated.
- [ ] No 5A-owned file modified (`git diff main --stat` shows only 5D-owned paths).
- [ ] `heavy_guard.sh` and the lock used for every local heavy job (log entries present).

**Phase 2**

- [ ] Physical robot built; link lengths within ±3 mm; directions match.
- [ ] Robot package and limits built for the generated robot.
- [ ] 5C wizards pass on the physical generated robot (homing, directions, safe poses).

## Fallbacks

- Round trip fails by end of Day 5 → hand-assembled arm made only from the modules (no agent), still own design; record the failure honestly.
- Generator placement unstable → fix the chain to one reference layout and vary only beam lengths.
- Missing parts → constrain the generator to available parts and regenerate; if still short, keep the robot virtual.
- Modal render problems → render a reduced set locally under `heavy_guard` at night.
- Physical build late (Day 7 gate) → skip sim → real in 6B; keep the VLA in simulation.
